# Universe Anime Planet — Telegram-бот (коллекционная гача-игра)

Единственный бот (второй отменён пользователем 2026-08-03 — не проектируем под него).

## Стек

- **Python 3.12**, `aiogram 3` (async, long polling на старте — вебхуки можно включить позже)
- **PostgreSQL** — источник правды по игровым данным (SQLAlchemy 2.0 async + asyncpg, миграции — Alembic)
- **Redis** (`redis.asyncio`) — тикеты, кулдауны, антидубликат-локи, лидерборды (sorted sets), кэш горячих данных
- **Docker / docker-compose** — bot + postgres + redis (+ позже api/web для Mini App), один `docker compose up -d`
- Оплата — ЮKassa для конвертации рублей → коины (донатная валюта), 1:1, через стандартный Telegram Bot Payments (см. "Донат" ниже) — не Stars, не прямой REST API ЮKassa
- **Telegram Mini App** (просмотр коллекции карточек по вселенным) — отдельный тонкий **FastAPI**-сервис, read-only, переиспользует те же SQLAlchemy-модели/БД, что и бот. Авторизация — валидация `initData` от Telegram WebApp (HMAC по bot token), без паролей/сессий. Фронтенд — статика (Vite + React/Preact, минимальный бандл), отдаётся через Caddy/nginx (нужен HTTPS — обязательное требование Telegram для Mini Apps). Это read-only витрина, она не пишет в БД напрямую и не дублирует игровую логику бота — все мутации (крутки, распыление и т.д.) остаются только в боте.

## Структура пакетов (подтверждено пользователем 2026-08-04)

Внутри `db/repositories/`, `services/`, `keyboards/`, `texts/`, `handlers/` — **никаких
плоских файлов на домен**. Каждый домен — своя папка с `__init__.py`, который
ре-экспортирует публичное API, и главным модулем, повторяющим имя папки:

```
services/card/card.py       (не services/card_catalog.py)
services/card/__init__.py   -> from bot.services.card.card import ...
```

Вызывающий код импортирует из пакета (`from bot.services.card import get_tier_map`),
а не через дублирование пути (`from bot.services.card.card import ...`) — `__init__.py`
существует именно чтобы этого избежать. Так масштабируется на любое число доменов и
оставляет место для соседних файлов внутри домена (`services/card/exceptions.py` и т.п.),
когда домен разрастётся.

Домены сейчас: `card`, `ticket`, `ubp`, `gacha`, `merge`, `dust`, `user`, `universe`,
`season`, `clan`, `inventory` (repositories/services), `common`/`settings`/`profile`/`deck`/
`collection` (keyboards/texts/handlers, по экрану бота, а не по данным).

**Осознанное исключение — `db/models/`.** Модели остаются плоскими файлами
(`db/models/user.py`, `db/models/card.py`, ...) — каждая уже является одним доменом сама
по себе (один класс, без соседних файлов), и `db/models/__init__.py` уже агрегирует их для
Alembic. Обернуть в те же папки можно, если пользователь явно попросит, но по умолчанию не делаем.

## `config/` и `constant/` — никаких значений "просто в коде" (подтверждено 2026-08-04)

Тот же принцип "домен = папка", применённый к двум типам переиспользуемых значений:

- **`config/`** — настраиваемые ЧИСЛА/параметры: `config/settings/settings.py` (pydantic
  `Settings`, читает `.env` — раньше был `bot/config.py`), `config/game/game.py` (баланс:
  шансы, лимиты тикетов, формулы UBP/пыли — раньше `bot/game_config.py`).
- **`constant/`** — строки, которые где-то СРАВНИВАЮТСЯ (`callback_data`, ключ Redis-лока,
  `reason` в `transactions`). Каждая — именованная константа в `constant/<домен>/<домен>.py`,
  домен соответствует тому, кто её строит/матчит (`constant/deck` — callback'и кнопок
  колоды, `constant/collection` — коллекции, `constant/gacha`/`merge`/`dust` — значения
  `reason` для audit-лога). Клавиатура, которая строит `callback_data=f"{CB_X}{id}"`, и
  хендлер, который матчит `F.data.startswith(CB_X)`, **всегда** импортируют один и тот же
  `CB_X` — никогда не дублируют строку. Это НЕ про игровой баланс (тот в `config/game`) —
  это про идентификаторы/ключи, где важно один раз задать значение и не разъехаться при
  переименовании.

Правило распространяется на весь новый код: если строка используется для `==`,
`.startswith()`, ключа словаря/Redis или как `reason`/`action` — она константа в
`constant/`, не строковый литерал в хендлере/клавиатуре/сервисе.

## Железо и нагрузка (жёсткие ограничения — учитывать в каждом решении)

- Сервер: 2 vCPU 3.3GHz, **2 GB RAM**, 40 GB диска
- Целевая нагрузка: до **30 000** одновременных игроков, данные — потенциально миллионы строк (инвентарь карточек)
- Вывод: Postgres-соединения через пул с небольшим лимитом (см. `POOL_SIZE` в конфиге), тяжёлые агрегации — в SQL, а не в Python; горячее состояние — в Redis, а не в Postgres.

## Обязательные инженерные правила (не нарушать)

1. **Ноль доверия к повторным нажатиям.** Бот может лагать, игрок может тапнуть кнопку дважды. Любое действие, которое тратит ресурс (тикет, пыль, коины) или проверяет КД, обязано быть атомарным на уровне БД: `UPDATE ... WHERE balance >= X RETURNING` или `SELECT ... FOR UPDATE` внутри транзакции. Никогда не читать баланс в Python отдельным запросом, а потом отдельно списывать — только атомарная операция.
2. **Идемпотентность callback'ов.** На время обработки конкретного действия ставится короткий Redis-lock по `user_id + action` (SET NX PX). Если лок не взят — молча игнорировать повторный клик (или `answer("Обрабатываю...")`), не выполнять действие второй раз.
3. **Минимум запросов к БД.** Никакого N+1. Джойны/агрегации — на стороне Postgres. Батчинг там, где можно (`executemany`, `INSERT ... SELECT`). Никаких Python-циклов по большим наборам ради подсчёта сумм/топов — это делает SQL.
4. **Горячие данные — в Redis, где это реально дешевле.** Активные КД, антидубликат-локи, топы по UBP (`ZADD`/`ZREVRANGE`) — в Redis, а не Postgres на каждое действие. Postgres — источник правды, Redis — горячий кэш с восстановлением из Postgres при промахе. Исключение: тикеты (см. "Модель тикетов" ниже) — их регенерация всё равно требует пересчёта по timestamp при каждом обращении, а списание/докупка обязаны быть атомарны в Postgres, поэтому кэшировать их в Redis отдельно смысла не даёт (один indexed UPDATE по PK — и так дёшево на 30k онлайн) — сознательно не стали городить второй слой.
5. **Всё асинхронно.** Никаких блокирующих вызовов в event loop (файлы, requests и т.п. — только через async-обёртки или executor).
6. **Индексы обязательны** на все поля фильтрации/сортировки: `user_id`, `universe`, `ubp`, `clan_id`, `season_id` и т.д.
7. **Пагинация везде**, где записей может быть много (топ игроков, `/players`, коллекция, список кланов). Никогда не тянуть таблицу целиком.
8. **Игровые числа — не магические константы.** Шансы дропа, лимиты, награды сезона/войны и т.п. — в одном месте конфигурации (модуль конфига или таблица), не разбросаны по хендлерам.
9. **Технический режим** — единая middleware, блокирующая все хендлеры кроме admin, когда включён режим техперерыва.
10. **Границы транзакций — на уровне логической операции, не на уровне функции.** `DbSessionMiddleware` даёт по одной `AsyncSession` на апдейт, но **не коммитит автоматически**. Функции в `db/repositories/*` и `services/*`, которые являются "листом" (один шаг, не композируются) — коммитят сами. Но если операция составная (например, крутка = списать тикет + добавить карту в инвентарь + начислить UBP), внутренние шаги **не должны коммитить сами** — коммит делает только верхнеуровневый сервис, ровно один раз, после всех шагов. Иначе при падении между шагами игрок теряет ресурс без результата (ровно то, чего просит избежать правило 1). Redis (лидерборд и т.п.) обновляем **только после успешного commit** в Postgres — иначе при откате транзакции Redis разъедется с источником правды. Если между шагами составной операции нужен вызов Telegram Bot API (например, казино: списать коины -> **бросить кубик через message.answer_dice()** -> начислить награду по результату) — I/O с Telegram делаем в хендлере между двумя вызовами сервиса на одной и той же сессии без промежуточного commit, коммит всё равно один, в самом конце (см. `services/casino`).
11. **`edit_text`/`edit_message_text` без `reply_markup` СОХРАНЯЕТ старую клавиатуру, не убирает.** Проверено (2026-08-05): Telegram Bot API трактует отсутствие `reply_markup` в запросе как "не менять", а не как "убрать". Если после редактирования сообщения старые кнопки не должны быть кликабельны (например, экран сменился на "введите число", а под ним всё ещё видны кнопки предыдущего меню) — передавать `reply_markup=InlineKeyboardMarkup(inline_keyboard=[])` явно. Не полагаться на дефолт.
12. **Нельзя `edit_text`↔`edit_media` конвертировать тип сообщения.** Если один и тот же логический экран иногда текст, иногда фото с подписью (например, карточка клана — фото, если у клана есть картинка, иначе текст, см. "Кланы" ниже) — Telegram не даёт отредактировать текстовое сообщение в фото и наоборот. Паттерн: удалить старое сообщение (проглотив ошибку, если уже нельзя удалить) и прислать новое нужного типа, вместо попытки угадать/подогнать тип существующего сообщения под новый контент (см. `handlers/clan/clan.py: _send_card`).

## Формат карточек (датасеты пользователя)

Пользователь кладёт файлы в:

```
assets/cards/<universe>/<ubpXXXX>UBP/<id>_<Name>.<ext>
```

Пример: `assets/cards/lookism/6000UBP/001_DanielEos.png`

- `<universe>` — папка вселенной (`onepiece`, `lookism`, `genshin`, ...)
- `<ubpXXXX>UBP` — базовый показатель UBP карты (влияет на шанс дропа и итоговую пыль при распылении)
- `<id>_<Name>` — числовой id карты и имя персонажа

Скрипт `scripts/seed_cards.py` сканирует `assets/cards/` и регистрирует/обновляет карточки в таблице `cards` (путь хранится в БД один раз, не пересчитывается на лету).

## Модель начисления UBP (подтверждено пользователем 2026-08-03)

`ubp_season`/`ubp_total` — **накопительный счётчик событий**, не live-пересчёт от текущей
коллекции (смена сезона обнуляет счётчик, но не трогает карточки — значит счётчик и
коллекция независимы). Два события начисляют UBP через единую точку
`services/ubp/ubp.py: award_ubp()` (атомарный UPDATE + audit-лог `transactions` +
синхронизация Redis-лидерборда), каждое — **в сезон, активный в момент события**:

1. **Крутка.** Карта выпадает всегда как 1★ — начисляется её `base_ubp`.
2. **Слияние.** 5 копий N★ → 1 копия (N+1)★, итоговый UBP = `base_ubp_N × 5 × 1.2` (round). Начисляется
   **только разница** между новым UBP и суммой 5 старых (`new_ubp - 5×old_ubp`), не полная
   стоимость смерженной карты — иначе задвоили бы то, что уже начислено при крутке этих 5 карт.
   Матем. упрощение: `new_ubp - 5×old_ubp = old_ubp×6 - old_ubp×5 = old_ubp` — то есть бонус
   слияния всегда равен ровно UBP одной исходной (домерженной) карты, независимо от звезды.
   Если слияние произошло в другом сезоне, чем крутка исходных карт — бонус уходит в сезон
   слияния, не в сезон крутки.
3. **Распыление** — на UBP не влияет, только начисляет пыль. Пыль за карту 1★ =
   `base_ubp // 1000`. Для смерженной карты множитель — **другой**, чем у UBP: пользователь
   явно сказал про 2★ карту "можно распылить как за 5 повторок" — то есть ×5 за звезду
   (`MERGE_COPIES_REQUIRED`), а не ×6 (`MERGE_MULTIPLIER`, которым считается сам UBP).
   Формула: `config.game.dust_for_stars(base_ubp, stars) = (base_ubp // 1000) × 5^(stars-1)`.
   Не путать с `ubp_for_stars()` — разные множители, разные формулы, обе в `config/game/game.py`.

## Модель тикетов (подтверждено пользователем 2026-08-03)

`TICKET_NATURAL_CAP = 3` — это потолок только для **пассивной регенерации** (1 тикет/2ч):
регенерация не добавляет тикеты сверх 3. Но докупка (магазин за коины/пыль) и промокоды могут
дать игроку сколько угодно тикетов сверх этого — баланс ничем не ограничен сверху (отображается
как `текущее/3`, например `150/3`). Крутка x10 тратит 10 тикетов из общего баланса — она
физически возможна только благодаря докупленным/подаренным тикетам, обычным реген это не
покрывает (за 20 часов набежит максимум 3).

Регенерация считается лениво и атомарно одним `UPDATE ... WHERE id=` (CTE с `FOR UPDATE`,
см. `services/ticket/ticket.py`), с ключевым нюансом анти-эксплойта: пока `tickets_count >= 3`,
таймер регена (`tickets_updated_at`) **замораживается на "сейчас"** при каждом обращении —
иначе после долгого простоя с большим запасом купленных тикетов, при падении баланса ниже 3
из-за трат, игрок получил бы мгновенный "рывок" накопленного (но не потраченного) регена за
всё время простоя. Замена условия "заморозки" на honest "накопление с последнего фактического
списания" была бы багом дюпа тикетов.

## Кланы (реализовано 2026-08-05)

- **UBP клана — живая агрегация, не денормализованная колонка.** `SELECT COALESCE(SUM(users.ubp_season/ubp_total),0) WHERE clan_id=...`, а не счётчик на `Clan`, обновляемый при каждом начислении UBP игроку. При максимум 15 участниках на клан (`MAX_CLAN_MEMBERS`) агрегация дешевле, чем городить синхронизацию, и не завязывает `services/gacha`/`services/merge` на существование клана.
- **Прогресс войны — снимок + живая разница, не Redis-счётчик.** На старте войны (`services/clan/war.start_war`) сохраняется `ClanWar.ubp_a_start`/`ubp_b_start` (текущий UBP сезона обоих кланов); прогресс на экране войны = `текущий UBP - снимок`. Не нужно инкрементить ничего при каждом начислении UBP игроку.
- **Война финализируется лениво.** В проекте нет фонового шедулера — `services/clan/war.get_progress()` при каждом вызове проверяет `now >= ends_at` и, если война ещё `active`, сама её завершает (награда победителю + `UPDATE status='finished'`) прямо в момент просмотра экрана войны любым участником. Это значит результат войны виден только тому, кто первым откроет экран войны после истечения таймера — дальше статус уже `finished`, второй заход покажет "нет активной войны".
- **Максимум 1 owner и 1 deputy на клан — гарантия на уровне БД**, не только в Python: частичный уникальный индекс `(clan_id, rank) WHERE rank IN ('owner','deputy')` на `clan_members`. Следствие: `transfer_ownership` обязан сначала понизить старого owner до member, потом повысить нового — если сделать наоборот, второй `UPDATE` упадёт на констрейнте.
- **`clan_join_requests` — одна таблица на заявки И приглашения**, направление отличает `is_invite`. **Заявка (не приглашение) разрешена только в ОДИН клан одновременно** — изначально (2026-08-05, первая версия) заявки в несколько кланов сразу были разрешены, но пользователь явно попросил ограничить: "подал заявку в 20 кланов, один принял, 19 висят — непонятно что с ними делать". `services/clan.apply_to_clan` бросает `AlreadyAppliedElsewhereError`, если у игрока уже есть заявка в другой клан (`clan_repo.get_application_for_user`); race не нужно защищать доп. констрейнтом — Redis-лок на кнопке "Подать заявку" (`LOCK_ACTION_APPLY_CLAN`) ключуется по `user_id`, а НЕ по паре `user_id+clan_id`, поэтому уже сериализует заявки в разные кланы от одного игрока. Приглашений (is_invite=true), в отличие от заявок, можно получить сколько угодно сразу — ограничение только на исходящие заявки игрока. При принятии заявки/приглашения все остальные заявки/приглашения этого игрока снимаются (`delete_all_join_requests_for_user`), чтобы не остаться "наполовину" в списке ожидания других кланов.
- **Картинка клана — Telegram `file_id`, не локальный путь.** В отличие от карточек персонажей (`assets/cards/...`, загружаются администратором через `scripts/seed_cards.py`), картинку клана присылает в чат сам игрок — в проекте нет пайплайна сохранения таких файлов на диск, поэтому `Clan.image_path` в этом случае хранит `file_id`, а не относительный путь. Ставить/менять картинку может только клан из топ-10 по UBP за всё время (`CLAN_TOP_IMAGE_ELIGIBLE_COUNT`), проверка — в сервисе (`services/clan.set_image`), а не только в UI. Карточка клана рендерится фото с подписью, если `image_path` задан, иначе текстом — см. правило 12.
- **Уведомления о заявках/приглашениях — отдельный тумблер, не общий `notifications_enabled`.** `User.notify_clan_requests` (Настройки -> Уведомления, подтверждено пользователем 2026-08-05) гейтит ровно два сообщения: владельцу — о новой заявке (`handlers/clan/clan.py: cb_apply_clan`), приглашённому игроку — о приглашении (`handlers/clan/requests.py: apply_invite`) — оба места, где получатель дальше сам соглашается/отказывает. FYI-уведомление "твою заявку приняли" (`handlers/clan/requests.py: cb_accept_application`) и уведомление обменника пыли (`handlers/clan/exchange.py`) остались на общем `notifications_enabled` — их пользователь не просил переносить.
- **Обменник обобщён с пыли на пыль/тикеты/коины (2026-08-06).** `services/clan/exchange.py: exchange_currency()` — одна функция на все 3 валюты вместо трёх копий `exchange_dust`, ветвится по `TransactionCurrency` на пару spend/add-вызовов (тикеты — через `services/ticket.spend/grant`, не напрямую в БД, чтобы не терять лениво накопленный реген перед списанием). UI получил промежуточный шаг выбора валюты (`CB_CLAN_EXCHANGE_CURRENCY_PREFIX`) перед вводом `@username сумма` — выбор кладётся в FSM-данные состояния `waiting_exchange_input`, а не в отдельный callback на каждую валюту.

## Сезонный пасс (реализовано 2026-08-05)

- **Уровень — не хранится, считается на лету из `User.ubp_season`** (`config/game.battle_pass_level_from_ubp`), по явной таблице стоимости уровней `BATTLE_PASS_LEVEL_UBP_COST` (продиктована пользователем, не единая формула — три сегмента: 2000 UBP/уровень до 10, потом растущий шаг до 20, потом до 30). Тот же принцип "живая агрегация вместо денормализованной колонки", что и UBP клана.
- **Премиум-ветка — разовая разблокировка НА СЕЗОН, покупается один раз, без продлений по дням (уточнено пользователем 2026-08-06 — исходная версия ошибочно завела ещё и `User.premium_pass_until`, день-таймер с "первая покупка / продление", который путал экран магазина; убран).** `BattlePass.is_premium` — булев-флаг "премиум-ветка сезона открыта навсегда", выставляется один раз при покупке (`services/shop.buy_premium_pass` → `services/battle_pass.set_premium`), повторная покупка в том же сезоне блокируется (`AlreadyPremiumError`). `User.premium_pass_until` остался в схеме как неиспользуемая колонка (миграцию на удаление не гнали) — ничего в неё больше не пишет и не читает.
- **Забрать награды — одной кнопкой сразу все уровни.** `claimed_free_level`/`claimed_premium_level` хранят high-water mark (до какого уровня уже забрано), не набор конкретных уровней. Кнопка "Забрать" в `services/battle_pass.claim_free`/`claim_premium` суммирует награды всех уровней от `claimed_*_level+1` до текущего и начисляет разом, одной транзакцией.
- **Награды на уровнях — формулой, не статичной таблицей** (см. правило 8): бесплатная ветка — пыль `10×уровень`; премиум — **дополнительно** к бесплатной (не вместо) пыль `20×уровень`; тикеты и коины — на уровнях-чекпоинтах (5/10/.../30 для тикетов, 10/20/30 для коинов премиум-ветки). Содержимое наград — решение автора кода (пользователь явно доверил составить численно), сама структура (две ветки, премиум дополняет бесплатную) — подтверждена пользователем.

## Подписка (реализовано 2026-08-05)

До этого момента подписка (Этап 6) была чистой покупкой таймера без единого игрового
эффекта. Теперь, пока `User.subscription_until` в будущем:

- **Тикет-реген вдвое быстрее** — 1 тикет/час вместо 1/2 часа (`TICKET_REGEN_INTERVAL_SECONDS_SUBSCRIBED`).
  Условие проверяется прямо внутри атомарного SQL `services/ticket._REGEN_AND_SPEND_SQL`
  (`CASE WHEN subscription_until > now() THEN ... ELSE ...`), а не отдельным запросом в
  Python — та же строка уже заблокирована `FOR UPDATE`, доставать `subscription_until`
  вторым походом в БД смысла нет.
- **+5 тикетов раз в 24 часа**, сверх капа. Считается **по факту** — если подписчик не
  заходил 3 дня, придёт сразу +15 (не 5), в отличие от обычного тикет-регена, который вместо
  этого "замораживает" таймер на капе (см. "Модель тикетов" выше). Это осознанно разное
  поведение: заморозка регена — это анти-эксплойт (не дать бесконечно копить реген без
  трат), а суточное начисление подписки — это платный бонус, который должен доставаться
  полностью, а не срезаться простоем игрока. Подтверждено пользователем 2026-08-05.
  Якорь — `User.subscription_ticket_granted_at`, выставляется **один раз** при первой
  покупке подписки (`extend_subscription`, только если ещё `NULL` — повторная
  покупка/продление уже активной подписки таймер не сбрасывает).

**Первый и единственный фоновый таск в проекте** (`main.py: _notify_sweep_loop`, раз в
`services/notify.SWEEP_INTERVAL_SECONDS` = 5 минут) — потому что начисление +5/сутки и два
push-уведомления ниже физически не могут быть ленивыми: игрок должен их получить, даже если
не открывает бота. Всё остальное в проекте по-прежнему либо реагирует на действие игрока,
либо считается лениво при заходе на экран (войны кланов и т.п.) — заводить полноценный
шедулер (Celery и т.п.) ради этого не стали, обычный `asyncio.create_task` с `sleep` в
`main.py` достаточен при нагрузке 30k игроков и не добавляет новых зависимостей/контейнеров.

**Push-уведомления (Настройки -> Уведомления, два независимых тумблера, подтверждено
пользователем 2026-08-05):**

1. **"Тикеты заполнены"** — только подписчикам (`User.notify_tickets_full`). Шлётся, когда
   бак на капе (3/3) дольше часа — и переиспользует тот же анти-эксплойт-приём, что и обычный
   тикет-реген: при отправке шедулер сам "трогает" `tickets_updated_at` (выставляет на
   `now()`), ровно как это сделал бы обычный заход игрока в приложение. Это одновременно и
   защищает инвариант заморозки, и естественно троттлит напоминание раз в час — активный
   игрок, открывающий бота, уже сам бампает эту колонку своими действиями и лишних пушей не
   получит.
2. **"Пора крутить" раз в 12 часов** — всем игрокам, не только подписчикам
   (`User.notify_roll_reminder`), безусловно (не проверяет баланс тикетов). Якорь —
   `User.roll_reminder_sent_at`, `server_default=now()` — первое напоминание приходит через
   12ч ПОСЛЕ регистрации, не сразу же после `/start`.

Оба тумблера читает/пишет `services/notify` через bulk `UPDATE ... RETURNING` (один запрос
на всех подходящих игроков разом, не цикл в Python по каждому — см. правило 3), рассылка
самих сообщений — через общий `utils/notify.notify()` (best-effort, глотает
`TelegramAPIError`, если игрок заблокировал бота).

## Донат (подтверждено пользователем 2026-08-05)

**Осознанный риск, зафиксирован явно.** По правилам Telegram (developer ToS) цифровые товары
внутри бота обязаны продаваться за Telegram Stars — сторонние платёжные провайдеры (в т.ч.
ЮKassa) официально разрешены только для физических товаров. Коины — по факту цифровой товар
(игровая валюта), так что формально это нарушение. Пользователь принял это решение осознанно
и попросил всё равно делать через ЮKassa/рубли, без Stars — не переспрашивать повторно.

**Механизм — НЕ прямой REST API ЮKassa**, а стандартный Telegram Bot Payments:

1. ЮKassa подключается один раз через BotFather → Bot Settings → Payments → ЮKassa. На выходе —
   `provider_token` (у пользователя уже есть тестовый, вида `381764678:TEST:181121`) —
   это НЕ shop_id/secret_key с сайта ЮKassa, кладётся в `.env` как `YOOKASSA_PROVIDER_TOKEN`.
2. Бот: `sendInvoice(provider_token=..., currency="RUB", prices=[LabeledPrice(...)])`. Суммы —
   в копейках (минимальные единицы валюты), не в рублях напрямую.
3. Telegram сам показывает форму оплаты и общается с ЮKassa — отдельный вебхук/поллинг от
   ЮKassa нашей стороной **не нужен**.
4. Обязательно должны обработать `pre_checkout_query` — ответить `answerPreCheckoutQuery(ok=True/False)`
   в течение 10 секунд, иначе Telegram отменит платёж. Затем прилетает `Message.successful_payment`.
5. Идемпотентность зачисления коинов — по `telegram_payment_charge_id` (уникальный constraint в
   `payments`), а не по какому-либо id от ЮKassa — Telegram может повторно доставить апдейт.

Пакет `yookassa` (PyPI) в зависимостях не нужен — вся оплата идёт через Bot API aiogram, без
прямого обращения к API ЮKassa с нашей стороны.

**Реализация (2026-08-05).** `pre_checkout_query` отвечает `ok=True` мгновенно, без похода в
БД — инвойс создаём только сами (`handlers/donate: _send_invoice`), сумма в нём валидна по
построению, а SLA 10 секунд важнее любой доп. проверки. Идемпотентность зачисления —
`db/repositories/payment.create_succeeded` (`INSERT ... ON CONFLICT DO NOTHING` по
`telegram_payment_charge_id`), не Redis-лок (правило 2 про лок — это защита от повторного
клика в UI, а здесь источник повтора — сервер Telegram, может передоставить апдейт).
**Критичный фикс существующих middleware**: `BanCheckMiddleware`/`TechModeMiddleware`
пропускают `Message` с `successful_payment` без блокировки независимо от бана/техрежима —
деньги Telegram списывает ДО доставки этого апдейта боту, значит блокировка апдейта = забрать
деньги игрока и не начислить коины без возврата. Не путать с блокировкой ЭКРАНА доната
(кнопка/команда) — та отдельно и нормально блокируется тем же middleware до создания
инвойса, тут риска нет (деньги ещё не списаны).

## Админ-панель (реализовано 2026-08-06)

- **Права — конфиг ИЛИ БД, с коротким замыканием.** `ADMIN_IDS` из `.env` — супер-админы, проверка чистая (множество в памяти, без похода в БД). `User.is_admin` — доп. админы сверх конфига, простой булев флаг, не отдельная таблица (подтверждено пользователем 2026-08-05: гибкость на будущее не требовалась). `services/admin.is_admin()` сначала проверяет конфиг, в БД лезет только если там пусто.
- **Весь `/admin` роутер закрыт одним фильтром, навешанным на роутер-агрегатор, а не в каждом файле.** `filters/admin.py: IsAdminFilter` стоит на `handlers/admin/__init__.py: router` (родитель, `Router(name="admin_root")`), а не в `handlers/admin/admin.py`/`season.py`/... по отдельности — фильтры каскадируют через `include_router` от родителя к детям, поэтому одной регистрации на верхнем уровне достаточно для всех вложенных `admin_*` роутеров (season/promo/referral/broadcast/mass_grant/delete_account). Не-админам ничего не отвечает (не "нет доступа", а тишина — как для незнакомой команды), чтобы не подсказывать посторонним, что админка вообще существует.
- **`TechModeMiddleware` не проверяет `User.is_admin` в БД на каждый апдейт** — это было бы лишним запросом на все 30k игроков ради редкой фичи. Порядок проверки: сначала конфиг-админы (бесплатно), потом Redis-флаг техрежима (уже было) — и только если техрежим ДЕЙСТВИТЕЛЬНО включён и юзер не конфиг-админ, тогда уже смотрим `is_admin` в БД. Техрежим почти всегда выключен, так что этот путь почти никогда не выполняется.
- **"Онлайн" = активны за 24ч** (`User.last_active_at`, подтверждено пользователем 2026-08-05) — у long-polling бота нет понятия текущего подключения. Колонка обновляется **тем же `UPDATE`**, что `BanCheckMiddleware` и так делает на каждый апдейт для бан-чека (`UPDATE users SET last_active_at=now() WHERE id=... RETURNING is_banned`) — не отдельным запросом сверху, тот же принцип, что и у тикетов (правило 4).
- **`psutil` — только через `asyncio.to_thread`.** Это блокирующие syscalls (CPU/RAM/диск), а правило 5 запрещает блокировать event loop — `services/admin/stats.py: _read_server_stats()` синхронная, вызывается исключительно через `to_thread`. `cpu_percent(interval=None)` — не `interval=0.1`, иначе полусекундная блокировка (даже через to_thread это держит поток экзекьютора без нужды).
- **Выдача карточки не пишет `Transaction`** — у `TransactionCurrency` нет варианта "карта" (только dust/coins/ubp_season/tickets), и обычная крутка тоже не логирует карту через Transaction (только начисленный UBP) — выдача админом карточки просто переиспользует `db/repositories/inventory.add_card`, ту же атомарную upsert-функцию, что и гача.
- **Массовые выдачи и смена сезона — SQL делает фан-аут, не Python-цикл.** `services/admin/mass_grant.py` — один `UPDATE` на всех игроков + `INSERT ... SELECT` в `transactions` из того же набора обновлённых строк (writable CTE) одним запросом на каждое действие; аналогично `start_new_season` переносит `ubp_season → ubp_total` одним `UPDATE` без `WHERE`. На 30k+ игроков цикл в Python по каждой строке нарушил бы правило 3 и держал бы транзакцию открытой неоправданно долго.
- **Рассылка — фоновый `asyncio.create_task`, не `await` прямо в хендлере.** Рассылка 30k игрокам батчами по 25 с паузой между батчами растянется на минуты — незавершённый хендлер держал бы Telegram-апдейт "в обработке" неадекватно долго. Фоновой задаче нужна СВОЯ сессия БД: `session` из `data` живёт только на время хендлера и закрывается вместе с ним, поэтому `session_factory` теперь тоже передаётся в workflow data (`dp.start_polling(..., session_factory=...)`, см. `main.py`) — вторая (после `services/notify`) причина, по которой он понадобился. Ссылку на созданный `asyncio.Task` держим в module-level `set()` с `add_done_callback` на удаление — иначе таск может быть собран сборщиком мусора до завершения (задокументированная особенность `asyncio.create_task` без сохранённой ссылки).
- **Промокоды: гонка на лимите активаций закрыта условием в `UPDATE`, не Redis-локом.** `used_count = used_count + 1 WHERE max_uses IS NULL OR used_count < max_uses` — сравнение идёт с ТЕКУЩИМ состоянием строки на момент выполнения, не со снимком, прочитанным раньше в Python. Если инкремент не прошёл (лимит уже исчерпан конкурентным запросом) — `session.rollback()` отменяет уже вставленную запись активации в той же транзакции, не начисляя награду дважды или никому.
- **Удаление аккаунта: `Clan.owner_id` (`RESTRICT`) — единственная таблица, не покрытая каскадом.** Все остальные связи с `users` — `ondelete=CASCADE` (карточки, транзакции, платежи, промо-активации, реф-визиты, участие в клане), поэтому `DELETE FROM users` обычно самодостаточен. Владелец клана с другими участниками блокирует удаление (`OwnerBlockedError`) — принудительной передачи владения ЗА игрока пока нет, это сознательный вырез из объёма, не баг. Владелец-единственный-участник — клан удаляется вместе с ним первым же `DELETE`, дальше каскад подчищает всё сам.

## Mini App (реализовано 2026-08-06)

- **`api` — тот же Docker-образ, что и `bot`, не отдельный Dockerfile.** Оба сервиса собираются из корневого `Dockerfile` (тот же `src/`, то же `requirements.txt`, теперь с `fastapi`/`uvicorn`) — у `api` в `docker-compose.yml` просто переопределена `command:` на `uvicorn api.main:app`. Один образ, меньше дублирования, укладывается в "переиспользует те же SQLAlchemy-модели/БД, что и бот" из require спеки.
- **Картинки карточек отдаёт Caddy напрямую, не FastAPI.** `/cards/*` в `Caddyfile` смонтирован на ту же `assets/cards`, что видит бот — бинарные файлы не гоняются через Python-процесс, `api` только возвращает `image_url` строкой (`/cards/<image_path>`, относительный — резолвится браузером в тот же origin).
- **Same-origin вместо CORS.** Caddy проксирует и статику фронтенда (`/`), и API (`/api/*`) под ОДНИМ доменом — браузер видит один origin, CORS-заголовки не нужны в проде. `CORSMiddleware` в `api/main.py` (allow all) — только для локальной разработки `vite dev` отдельно от Caddy на другом порту.
- **`initData` — единственная авторизация, HMAC по bot token, с защитой от replay.** `api/auth.py` следует официальному алгоритму Telegram (data-check-string из отсортированных пар, `HMAC-SHA256(key=HMAC-SHA256("WebAppData", bot_token), data_check_string)`), плюс доп. проверка `auth_date` не старше 24ч — Telegram сам не ограничивает срок жизни initData, перехваченный старый initData иначе был бы валиден вечно.
- **`/api/universes` — вселенные ИГРОКА, не общий список активных вселенных бота.** "Список вселенных игрока" в исходном ТЗ — это те вселенные, где у него есть хотя бы одна карта (`inventory.list_owned_universes`, JOIN с `user_cards`), не статичный список из `universes.is_active=true`. Игрок может иметь карты в нескольких вселенных, даже если сейчас выбрана для крутки только одна (`User.universe_selected`) — коллекция не сбрасывается при переключении вселенной.
- **Домен — обязательное условие, не опция.** Let's Encrypt (через Caddy) выдаёт сертификат по домену, не по IP, а без валидного HTTPS Telegram вообще не откроет Mini App. `DOMAIN`/`MINI_APP_URL` в `.env` по умолчанию пустые — сервисы `api`/`caddy` тогда просто не поднимают (остальной бот полностью самодостаточен без них), кнопка "🖼 Коллекция (веб)" в главном меню не показывается (`main_menu(mini_app_url=...)` — `None`/пусто прячет кнопку, а не ведёт на битую ссылку).
- **Фронтенд — Vite + Preact + TypeScript**, выбрано пользователем как "лучший долгосрочный/масштабируемый вариант" 2026-08-06 (альтернатива — React или сборка без бандлера через CDN): Preact даёт компактный бандл (важно для загрузки в Telegram WebView на мобильных сетях) при совместимости с React-экосистемой через `preact/compat`, если понадобится; Vite — нормальные инструменты на вырост (роутинг, code-splitting, TS). Собирается мульти-стейдж `Dockerfile.web` (node только на стадии сборки, в финальном образе — только caddy + `dist/`). **Не проверено локальным запуском** — в рабочем окружении нет npm/node, только визуальная проверка кода.
- **Тема Telegram — CSS-переменные выставляются вручную.** `Telegram.WebApp` не инжектит `--tg-theme-*` в CSS сам — `src/web/src/telegram.ts: applyTelegramTheme()` читает `themeParams` и сама пишет `document.documentElement.style.setProperty(...)` при старте; `styles.css` использует `var(--tg-theme-bg-color, <fallback>)` с фоллбэками на случай запуска вне Telegram (например, `vite dev` в обычном браузере).

## Антифлуд и fallback (реализовано 2026-08-06)

- **`ThrottlingMiddleware` — самый внешний middleware, до `DbSessionMiddleware`.** Порядок в `main.py`: throttle → db → tech_mode → ban_check. Смысл именно в таком порядке — спам-апдейт отбрасывается ДО открытия сессии Postgres, не тратя соединение из и так небольшого пула (`db_pool_size=5`, см. "Железо и нагрузка") на то, что всё равно будет проигнорировано. Троттлинг — `SET NX PX` в Redis по `user_id` (не по action, в отличие от `action_lock`, см. правило 2) — это защита от спама ЛЮБЫМИ апдейтами вперемешку, а не от повторного клика по одной кнопке.
- **`handlers/fallback` обязан быть последним в `get_routers()`.** aiogram пробует роутеры по порядку регистрации; catch-all без фильтров (`@router.message()`/`@router.callback_query()` без аргументов) заберёт СЕБЕ любой апдейт, если стоит раньше домена, которому апдейт предназначался. Он безопасен как последний, потому что каждый FSM-флоу в проекте уже сам валидирует "не то прислали" на уровне СВОЕГО состояния (см. паттерн `StateFilter(...)` без доп. условий в handlers/*) — fallback перехватывает только то, что вообще ничей.
- **Сворачивание reply-меню разрешено явно (изменено 2026-08-06).** Изначально `main_menu()` держала `is_persistent=True` (осознанное решение — потерять доступ к навигации хуже, чем не иметь кнопки "скрыть"). Пользователь явно попросил вернуть возможность сворачивать клавиатуру — `is_persistent=False`, даёт клиенту Telegram показать стандартную стрелку сворачивания рядом с поле ввода. Это НЕ отдельная кнопка в самой клавиатуре (той риск случайного тапа, из-за которого раньше отказались, не относится) — стандартный элемент интерфейса Telegram.

## Рефералы (реализовано 2026-08-06)

- **Личные ссылки игроков — отдельная сущность от именных кампаний админа.** `ReferralLink`/`ReferralVisit` (см. "Админ-панель") — под кампании из `/admin`, диплинк `ref_<код>`. Личная ссылка игрока — `t.me/<bot>?start=r_<user_id>` (префикс `r_`, короче и без коллизий с `ref_` — второй символ после `r` разный: `_` против `e`), хранится не отдельной таблицей, а колонкой `User.referred_by_id` — просто "кто меня привёл", выставляется ОДИН раз при первом `/start` по такой ссылке (`db/repositories/user.set_referred_by`, `WHERE referred_by_id IS NULL`) и никогда не меняется. Нельзя указать себя же реферером и реферер обязан существовать (иначе FK-нарушение) — обе проверки в `handlers/start` до вызова `set_referred_by`.
- **Награда за приглашённого — только после его ПЕРВОЙ крутки, не сразу при `/start`.** Подтверждено пользователем 2026-08-06: сразу при регистрации легко накрутить наградами через пустые аккаунты. `services/gacha._roll()` бесплатно узнаёт "это была первая крутка вообще" из `RETURNING` того же `UPDATE`, что инкрементит `total_rolls` (`new_total_rolls == count` ⟺ старое значение было 0) — без отдельного `SELECT` перед инкрементом.
- **10% с донатов реферала — начисляется рефереру при КАЖДОМ его успешном платеже**, пока связь `referred_by_id` не разорвана (округление вниз, `services/donate.credit_payment`) — не разовая награда, а вечный процент, пока игрок остаётся привязан к рефереру.
- **Статистика на экране "Рефералы" — живая агрегация, не денормализованные счётчики** (тот же принцип, что UBP клана/прогресс коллекции): перешло/играет — прямой `COUNT` по `users.referred_by_id`; заработано (коины/тикеты) — `SUM` по `transactions.reason IN (referral_reward, referral_donate_cut)`, а не отдельная колонка-счётчик на `User`. По запросу пользователя 2026-08-06 экран также показывает донатеров/подписчиков/владельцев Battle Pass среди рефералов — три небольших отдельных запроса (не один гигантский с кучей `LEFT JOIN`), это не горячий путь (один игрок открывает свою же статистику по кнопке), читаемость важнее экономии round-trip'а.
